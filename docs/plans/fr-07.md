## T1. 응답 DTO와 Repository 조회 쿼리

**변경 파일**
- 신규 `enrollment/MyEnrollmentResponse.java`: record `(Long id, String courseTitle, Long sessionId, Instant sessionStartAt, String sessionPlace, EnrollmentStatus status, Integer waitingNumber, Instant appliedAt)`. Javadoc에 "`waitingNumber`는 WAITING일 때만 값이 있다(D-23)".
- 신규(필요하면) `enrollment/MyEnrollmentRow.java`: 같은 필드에 `waitingNumber`만 `Long`인 package-private record와 `MyEnrollmentResponse toResponse()`(`Math.toIntExact`). JPQL `select new`가 서브쿼리의 Long을 Integer 생성자에 맞추지 못할 때만 둔다.
- `enrollment/EnrollmentRepository.java`: 메서드 추가
  ```java
  @Query(value = "<설계명세 3.1의 JPQL>", countQuery = "<설계명세 3.2의 JPQL>")
  Page<MyEnrollmentRow> findMyEnrollments(
      @Param("employeeId") String employeeId,
      @Param("status") EnrollmentStatus status,   // null이면 전체
      Pageable pageable);
  ```
  - `order by e.appliedAt desc, e.id desc`는 JPQL에 직접 쓴다. 호출자는 정렬 없는 `Pageable`을 넘긴다.
  - JPQL의 상태 리터럴은 기존 쿼리처럼 `'WAITING'`으로 쓰거나 enum 상수 경로(`com.example.eduhub.enrollment.EnrollmentStatus.WAITING`)를 쓴다. 둘 중 이 Hibernate 버전에서 통과하는 쪽을 쓴다.

**테스트** `EnrollmentRepositoryTest`(설계명세 7.1 R1~R7)
- 기존 헬퍼 `saveCourse`, `saveSession`, `enrollment(...)`를 재사용한다. 대기 행은 `Enrollment.waiting(..., key)`로 키를 직접 준다.
- R3은 같은 행에 대해 `WaitingNumbers` 식(`countBySessionIdAndStatusAndWaitingKeyLessThan + 1`)과 값이 같은지 단언한다.
- R4는 음수 키(예: -1, 1, 2)를 넣고 순번 1·2·3을 확인한다.
- R6은 `appliedAt`이 같은 두 건을 넣고 id 내림차순을 확인한다.

**완료 명령**
```bash
./gradlew spotlessApply test --tests "*EnrollmentRepositoryTest"
```

**검토 포인트**
- `(:status is null or e.status = :status)`가 null·값 모두에서 맞게 동작하는가
- 서브쿼리가 같은 회차(`w.session = s`)와 `WAITING`만 세는가. 취소된 행(키 NULL)이 섞이지 않는가
- count 쿼리의 조건이 목록 쿼리와 같은가

## T2. 조회 서비스

**변경 파일**
- `enrollment/EnrollmentQueryService.java`
  ```java
  public PageResponse<MyEnrollmentResponse> getMyEnrollments(
      String employeeId, EnrollmentStatus status, Pageable pageable)
  ```
  - `PageRequest.of(pageable.getPageNumber(), pageable.getPageSize())`로 정렬을 버리고 Repository를 호출한다(`CourseQueryService.searchCourses`와 같은 방식).
  - `PageResponse.from(page.map(MyEnrollmentRow::toResponse))`. 행 record를 생략했다면 그대로 감싼다.
  - 클래스 Javadoc을 "신청 조회(FR-05, FR-07)"로 고친다.

**테스트**
- 신규 `enrollment/MyEnrollmentsQueryCountTest.java`(설계명세 7.2)
  - `@SpringBootTest(properties = "spring.jpa.properties.hibernate.generate_statistics=true")`, `@ActiveProfiles("test")`
  - 데이터: 사원 1명, 과정 3개, 회차 4개. 확정 1, 대기 2(서로 다른 회차, 각 회차에 앞선 대기자를 둬 순번 2 이상), 취소 1. 다른 사원의 신청도 섞는다.
  - 데이터 준비는 `TransactionTemplate`이나 Repository 저장으로 커밋한 뒤, `SessionFactory`의 `Statistics.clear()`를 하고 서비스 `getMyEnrollments(employee, null, PageRequest.of(0, 20))`를 호출한다.
  - 단언: `getPrepareStatementCount()`가 1 이상 2 이하. 응답 4건의 과정 제목, 장소, 순번, 정렬.
  - `status=WAITING` 호출도 2 이하인지 확인한다.
  - 정리: 테스트가 만든 행을 `@AfterEach`에서 지운다(enrollment → session → course 순). 다른 테스트에 데이터를 남기지 않는다.
- `EnrollmentQueryServiceTest`(기존, Mockito 단위 테스트라면): 정렬이 담긴 `Pageable`을 넘겨도 Repository에는 정렬 없는 `PageRequest`가 전달되는지 확인한다.

**완료 명령**
```bash
./gradlew spotlessApply test --tests "*EnrollmentQueryServiceTest" --tests "*MyEnrollmentsQueryCountTest"
```

**검토 포인트**
- 쿼리 수 측정이 데이터 준비 쿼리를 세지 않는가(Statistics clear 시점)
- 테스트 데이터 정리로 다른 테스트(특히 사번이 같은 테스트)에 영향이 없는가

## T3. 사번 리졸버 (common)

**변경 파일**
- 신규 `common/CurrentEmployee.java`: `@Target(PARAMETER) @Retention(RUNTIME)`. Javadoc: "로그인한 사원의 사번. 인증(D-11) 전에는 `X-Employee-Id` 헤더(D-21)".
- 신규 `common/CurrentEmployeeArgumentResolver.java`(`HandlerMethodArgumentResolver`)
  - `supportsParameter`: `@CurrentEmployee`가 있고 타입이 `String`
  - `resolveArgument`: 헤더 `X-Employee-Id`를 읽어 없거나 공백이면 `InvalidRequestException("X-Employee-Id: 사번이 필요합니다")`, 20자를 넘으면 `InvalidRequestException("X-Employee-Id: 20자 이하여야 합니다")`. 값은 trim하지 않는다(기존 `@NotBlank @Size` 동작과 같게).
  - 헤더 이름은 상수로 두고 `// TODO(NFR-03): 인증 도입 후 인증 정보에서 사번을 꺼낸다`를 단다.
- 신규 `common/WebConfig.java`: `WebMvcConfigurer.addArgumentResolvers`로 등록.

**테스트**
- 신규 `common/CurrentEmployeeArgumentResolverTest.java`(설계명세 7.4): `MockHttpServletRequest`와 `ServletWebRequest`로 정상, 누락, 공백, 20자(통과), 21자(예외).

**완료 명령**
```bash
./gradlew spotlessApply test --tests "*CurrentEmployeeArgumentResolverTest"
```

**검토 포인트**
- 기존 세 엔드포인트의 동작이 바뀌지 않는가(`@CurrentEmployee`를 쓰지 않으므로 영향이 없어야 한다)
- 오류 응답이 `ErrorResponse`(`BAD_REQUEST`) 형식인가

## T4. Controller와 OpenAPI

**변경 파일**
- `enrollment/EnrollmentController.java`: 메서드 추가
  ```java
  @GetMapping("/api/v1/me/enrollments")
  public PageResponse<MyEnrollmentResponse> getMyEnrollments(
      @Parameter(hidden = true) @CurrentEmployee String employeeId,
      @RequestParam(required = false) EnrollmentStatus status,
      @Parameter(hidden = true) @PageableDefault(size = 20) Pageable pageable)
  ```
  - `@Operation(summary = "내 신청 내역을 조회한다", description = "status를 생략하면 전체. 신청 일시 최신순. WAITING이면 waitingNumber가 있다")`
  - 메서드에 `@Parameter(in = ParameterIn.HEADER, name = "X-Employee-Id", required = true, description = "신청자 사번. 인증 도입 전 임시")`
  - `page`, `size`는 `CourseController`처럼 `@Parameter(in = QUERY, ...)`로 문서화한다.
  - `@ApiResponse` 200(목록), 400(헤더 누락·공백·20자 초과, 알 수 없는 status, `ErrorResponse`)
  - 클래스 Javadoc에 FR-07을 추가한다.

**테스트**
- `EnrollmentControllerTest`(`@WebMvcTest`는 `WebMvcConfigurer`를 포함하므로 리졸버가 등록된다. 등록되지 않으면 `@Import(WebConfig.class)`)
  - 200: 서비스에 `("E1001", null, ...)`가 전달되고 JSON 필드(`content[0].courseTitle`, `waitingNumber`, `totalElements`)가 나온다.
  - `status=WAITING`이면 enum으로 전달된다.
  - 400: 헤더 누락, 공백, 21자, `status=UNKNOWN`. 응답 `code`가 `BAD_REQUEST`이고 서비스는 호출되지 않는다.
- `OpenApiDocsTest`: `$.paths['/api/v1/me/enrollments'].get.summary`, 응답 `200`·`400`, `parameters`에 `in=header`·`name=X-Employee-Id`가 있고 `employeeId`라는 쿼리 파라미터는 없다.

**완료 명령**
```bash
./gradlew spotlessApply test --tests "*EnrollmentControllerTest" --tests "*OpenApiDocsTest"
```

**검토 포인트**
- 사번을 요청 파라미터로 받는 경로가 없는가(NFR-03)
- 스펙에 헤더가 한 번만, 필수로 나오는가

구현 시 추가: 헤더 스키마에 maxLength 20(검증 규칙과 문서 일치).

## 위험 영역

| 위험 | 대응 |
|---|---|
| Hibernate 6 JPQL에서 `select new` 안의 `case` + 스칼라 서브쿼리, enum null 파라미터 | T1 Repository 테스트로 실제 MariaDB에서 확인. 안 되면 대안: 목록 쿼리(1회) + 대기 행들의 순번을 `session_id IN (...)` 한 번의 집계 쿼리로 구해 합침(총 3회 이하). 이때는 완료 기준(1~2개)과 달라지므로 개발자에게 보고한다 |
| 쿼리 수 측정이 count 생략 여부에 따라 1 또는 2 | 단언을 "1 이상 2 이하"로 둔다 |
| 헤더 위조(W2) | 이번 범위에서 해결하지 않는다. 리졸버 한 곳에 모아 인증 도입 시 바꾸기 쉽게만 한다 |
| 쿼리 수 테스트가 커밋된 데이터를 남김 | `@AfterEach` 정리, 고유한 사번 사용 |
