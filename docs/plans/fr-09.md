- 상태: **승인됨 (2026-11-24), T3 개정 같은 날**: 전체 테스트에서 AFTER_COMMIT + REQUIRES_NEW가 커넥션 풀 교착(C4·C7 30초 초과)을 일으켜, 개발자 결정으로 리스너를 BEFORE_COMMIT(같은 트랜잭션)으로 바꿨다(설계명세 2절 개정). T1·T2는 그대로다
- 설계명세: `docs/design/FR-09-notification.md` (승인됨). 결정 사항 D-32, 선행 D-20·D-24·D-26.
- 규칙: `CLAUDE.md`, `backend/CLAUDE.md`, `.claude/skills/eduhub-api/SKILL.md`, `.claude/rules/db-migration.md`
- 브랜치: `feature/fr-09-notification`
- 진행: 작업마다 implementer 구현 → reviewer 검토. 심각·경고는 implementer가 수정하고, 수정·재검토는 최대 2회.
- 모든 명령은 `backend/`에서 실행한다. 테스트는 로컬 MariaDB `eduhub_test`를 쓴다.
- **여러 계층 작업(CLAUDE.md 5):** 전체로는 새 패키지 `notification`(마이그레이션·엔티티·리스너)과 기존 `enrollment` 서비스 2개가 바뀐다(신규 6, 수정 2, 테스트 수정 2·신규 4 정도, diff 약 500줄 예상). 이 계획 승인으로 함께 승인받는다. T2는 기존 신청·승급 코드를 바꾸므로 시작 전에 한 번 더 알린다.

## T1. 스키마, 엔티티, Repository

**변경 파일**
- 신규 `src/main/resources/db/migration/V6__create_notification.sql`: 설계명세 5절 그대로(테이블 + `idx_notification_employee`). V1~V5는 수정하지 않는다.
- 신규 `notification/package-info.java`: 패키지 설명(`enrollment` 이벤트를 받아 알림을 기록한다. `enrollment`는 이 패키지를 참조하지 않는다).

- 신규 `notification/Notification.java` (`@Entity`, 테이블 `notification`)
  - 필드 `id`(IDENTITY), `employeeId`, `type`(`@Enumerated(STRING)`), `message`, `createdAt`(`Instant`)
  - JPA용 protected 기본 생성자, 생성자 `Notification(String employeeId, NotificationType type, String message, Instant createdAt)`, getter
- 신규 `notification/NotificationRepository.java`: `JpaRepository<Notification, Long>`, `List<Notification> findByEmployeeIdOrderByIdAsc(String employeeId)`(테스트·이후 조회용)

- `NotificationType` 메시지 문구 단위 테스트(같은 테스트 파일 또는 `NotificationTypeTest`)

## T2. 이벤트와 발행 (기존 코드 변경, 시작 전 개발자에게 알림)

**변경 파일**
- 신규 `enrollment/EnrollmentConfirmedEvent.java` (public record)
  - `Long enrollmentId, String employeeId, Long sessionId, Reason reason`
  - 중첩 `public enum Reason { APPLIED, PROMOTED }`
  - 정적 팩토리 `static EnrollmentConfirmedEvent applied(Enrollment)`, `promoted(Enrollment)`(package-private). 회차 id는 `enrollment.getSession().getId()`(LAZY 프록시의 id 접근은 초기화하지 않음)
- `enrollment/EnrollmentCommandService.java`
  - 생성자에 `ApplicationEventPublisher eventPublisher` 추가
  - `enroll`: `save(...)` 뒤 `saved.getStatus() == CONFIRMED`이면 `eventPublisher.publishEvent(EnrollmentConfirmedEvent.applied(saved))`. 대기면 발행하지 않는다
  - `cancel`: `// TODO(FR-09): 승급 알림` 주석 삭제(승급 알림은 `VacancyFiller`가 낸다)
- `enrollment/VacancyFiller.java`
  - 생성자에 `ApplicationEventPublisher eventPublisher` 추가
  - `saveAllAndFlush(promoted)` 뒤 승급자마다 `publishEvent(EnrollmentConfirmedEvent.promoted(e))`
  - Javadoc에 "승급자마다 `PROMOTED` 이벤트를 발행하며, 리스너는 커밋 뒤에 실행된다" 추가
- 패키지 의존 방향: `enrollment`는 `notification`을 import하지 않는다.

**테스트**
- `EnrollmentCommandServiceTest`: 생성자에 `@Mock ApplicationEventPublisher` 추가
  - 확정 저장 시 `APPLIED` 이벤트 1건(사번·회차 id·enrollmentId 검증, `ArgumentCaptor`)
  - 대기 저장 시 발행 없음(`verifyNoInteractions(eventPublisher)`)
  - 중복 신청 예외 시 발행 없음
- `VacancyFillerTest`: 생성자에 `@Mock ApplicationEventPublisher` 추가
  - 2명 승급 시 `PROMOTED` 2건(대기 키 순서대로)
  - 빈자리 없음·대기자 없음·시작 후에는 발행 없음
- `CapacityChangeEnrollmentHandlerTest`는 `VacancyFiller`를 모의 객체로 쓰므로 바뀌지 않는다(확인만).

**완료 명령**
```bash
./gradlew spotlessApply test --tests "*EnrollmentCommandServiceTest" --tests "*VacancyFiller*" --tests "*CapacityChangeEnrollmentHandlerTest"
```

**검토 포인트**
- 발행이 `saveAndFlush`/`saveAllAndFlush` 뒤(id 존재)인지
- 대기 저장·예외 경로에서 발행하지 않는지
- 락·트랜잭션 속성(`READ_COMMITTED`, `MANDATORY`) 불변
- `enrollment` → `notification` 의존이 생기지 않았는지

## T3. 리스너

**변경 파일**
- 신규 `notification/NotificationListener.java` (`@Component`, package-private 클래스 가능, 메서드는 public)
  - 생성자: `NotificationRepository`, `Clock`
  - (개정) `@TransactionalEventListener(phase = TransactionPhase.BEFORE_COMMIT)` `public void on(EnrollmentConfirmedEvent event)`. `@Transactional`은 붙이지 않는다(신청 트랜잭션에 참여)
    - `NotificationType type = event.reason() == APPLIED ? ENROLLMENT_CONFIRMED : WAITING_PROMOTED` (switch 식)
    - `repository.save(new Notification(event.employeeId(), type, type.messageFor(event.sessionId()), clock.instant()))`
    - `log.info("알림 기록(커밋 전): employeeId={}, type={}, enrollmentId={}, sessionId={}", ...)`
    - (개정) 저장 예외를 잡지 않는다. 그대로 전파되어 신청 트랜잭션이 롤백된다(try/catch와 ERROR 로그 제거)

**테스트**
- 신규 `notification/NotificationListenerTest`(Mockito, N7)
  - `APPLIED` → `ENROLLMENT_CONFIRMED`, 메시지·사번·고정 `Clock` 시각으로 저장
  - `PROMOTED` → `WAITING_PROMOTED`
  - (개정) 저장소가 `RuntimeException`을 던지면 `on()`이 같은 예외를 던진다(`assertThatThrownBy`)

**완료 명령**
```bash
./gradlew spotlessApply test --tests "*NotificationListenerTest"
```

**검토 포인트**
- (개정) BEFORE_COMMIT이고 `@Transactional`·`REQUIRES_NEW`가 없는지(추가 커넥션 없음)
- 로그에 개인정보가 사번 외에 없는지

## T4. 통합 테스트 (실제 MariaDB)

**변경 파일**
- 신규 `notification/NotificationIntegrationTest`(`@SpringBootTest`, `@ActiveProfiles("test")`, 클래스에 `@Transactional` 없음)
  - 준비는 `VacancySelfHealIntegrationTest`처럼 서비스·저장소로 과정·회차를 만들고, `@AfterEach`에서 이 테스트가 만든 신청·회차·과정과 **사번 접두어 `N9-`의 알림**만 지운다
  - 시나리오(설계명세 7절)
    - N1: 빈 회차 신청 → `N9-A` 알림 1건, `ENROLLMENT_CONFIRMED`, 메시지에 회차 id (**완료 기준**)
    - N2: `TransactionTemplate` 안에서 `enroll`(확정) 뒤 `RuntimeException` → 신청 0건, 알림 0건 (**완료 기준**)
    - N3: 정원 1 회차에 두 번째 신청 → 대기, 두 번째 사번 알림 0건
    - N4: 정원 1, 확정자 취소 → 대기자 `WAITING_PROMOTED` 1건, 취소자는 신청 시 1건만
    - N5: 정원 1 → 3 증가(`CourseCommandService` 회차 수정) → 대기 2명 각 1건
    - N6: 오래된 상태(확정 < 정원, 대기 있음, JDBC로 정원만 올림)에서 이미 활성 신청이 있는 사번이 다시 신청 → 409, 자기 복구 승급분 알림 0건이고 대기자도 그대로 대기
    - N9(개정): 알림 저장이 실패하면 바깥 트랜잭션도 롤백된다. `TransactionTemplate` 안에서 JDBC로 표식 행(예: 테스트 과정 1건)을 쓰고 사번 21자 이상인 `EnrollmentConfirmedEvent`를 직접 발행 → `execute`가 예외를 던지고 표식 행·알림 모두 0건(V6 `employee_id` VARCHAR(20) 초과로 INSERT 실패)
    - N10(개정): 기존 `EnrollmentConcurrencyTest` C1~C10이 교착 없이 통과하는지는 T4 완료 명령 뒤 전체 테스트로 확인한다
  - 리스너는 동기 실행이므로 서비스 호출이 돌아온 직후 바로 조회해도 된다(대기·폴링 불필요)

**완료 명령**
```bash
./gradlew spotlessApply test --tests "*NotificationIntegrationTest"
```

**검토 포인트**
- 커밋이 실제로 일어나는 구성인지(테스트 트랜잭션 없음)
- 정리 범위가 다른 테스트 데이터를 지우지 않는지
- N6의 409 경로가 실제로 자기 복구 뒤에 나는지(중복 검사는 `fillVacancies` 앞이므로, 앞 검사 통과 후 유일 제약 위반으로 409가 나는 경로가 필요하면 implementer가 판단해 기록. 어렵다면 N6은 "자기 복구 승급 뒤 `TransactionTemplate` 롤백"으로 대체)

## 위험 영역

| 위험 | 대응 |
|---|---|
| 롤백된 트랜잭션의 알림 저장 | AFTER_COMMIT이라 구조적으로 없음. N2·N6으로 확인 |
| 알림 실패가 신청을 롤백시킴(개정에서 받아들임) | INSERT가 단순해 실패 가능성이 낮다. N7·N9로 동작 고정 |
| 승급 경로 누락 | 승급은 `VacancyFiller`에만 있음(D-26). N4·N5로 취소·정원 증가 경로 확인 |
| 커넥션 풀 교착(A안에서 실제 발생) | BEFORE_COMMIT으로 추가 커넥션 제거. 전체 동시성 테스트로 확인 |
| 기존 동시성 테스트(C1~C10) 영향 | 알림 행이 늘어날 뿐 락 구간은 같음. 전체 `./gradlew test`로 확인 |
| 테스트 데이터 정리 | `notification`에 회차 id가 없으므로 사번 접두어로만 지운다 |
