## T1. 스키마, 상태, 엔티티, 남은 자리 계산

**변경 파일**
- 신규 `src/main/resources/db/migration/V5__add_enrollment_completed_at.sql`: `ALTER TABLE enrollment ADD COLUMN completed_at DATETIME(6) NULL;` (V1~V4 수정 금지)
- `enrollment/EnrollmentStatus.java`: `COMPLETED` 추가
- `enrollment/Enrollment.java`
  - `completedAt` 필드(Javadoc "수료 시각. COMPLETED일 때만 값이 있다(D-28)")와 getter
  - `void complete(Instant now)`: `CONFIRMED`가 아니면 `IllegalStateException`. 상태 `COMPLETED`, `completedAt = now`. `confirmedAt`은 그대로 둔다.
- `course/CourseSession.java`: `void ensureCompletable(Instant now)`
  - 시작 전이면 `ConflictException("SESSION_NOT_STARTED", ...)`
  - 그 밖에 OPEN이면 `ConflictException("SESSION_NOT_CLOSED", ...)`
  - CLOSED면 통과한다.
  - 검사 순서는 "시작 → 종료"다. 시작 전 회차는 종료될 수 없으므로(D-16) 결과는 같지만, 메시지가 원인을 바로 말하게 한다.
- `enrollment/EnrollmentRepository.java`: `countBySessionIdsAndStatus`를 상태 목록을 받는 `countBySessionIdsAndStatusIn(Collection<Long>, Collection<EnrollmentStatus>)`로 바꾼다(JPQL `e.status in :statuses`). 기존 호출처는 `EnrollmentSeatCounter`뿐인지 확인한다.
- `enrollment/EnrollmentSeatCounter.java`: `EnumSet.of(CONFIRMED, COMPLETED)`로 센다.
- `course/SessionSeatCounter.java`: 메서드 Javadoc을 "회차별로 자리를 차지한 신청(확정·수료) 수"로 고친다. 메서드 이름은 유지해 `course` 쪽 변경을 줄인다.

**테스트**
- `EnrollmentTest`(E1): 확정 → 수료(상태, `completedAt`, `confirmedAt` 유지). 대기·취소·수료에서 `complete`하면 예외이고 상태는 그대로다.
- `CourseSessionTest`(S1): 시작 전 → `SESSION_NOT_STARTED`, 시작 시각과 같은 now에 OPEN → `SESSION_NOT_CLOSED`, CLOSED → 통과.
- `EnrollmentRepositoryTest`
  - 수료 행을 저장하고 다시 읽으면 `completedAt`이 왕복된다(V5와 `validate`).
  - 수료 행은 `active_session_id`가 NULL이라 같은 사번의 새 활성 행과 충돌하지 않는다.
- `EnrollmentSeatCounterTest`(T1): 확정 2, 수료 1, 대기 1, 취소 1 → 3.

**완료 명령**
```bash
./gradlew spotlessApply test --tests "*EnrollmentTest" --tests "*CourseSessionTest" --tests "*EnrollmentRepositoryTest" --tests "*EnrollmentSeatCounterTest" --tests "*CourseQueryServiceTest"
```

**검토 포인트**
- `VacancyFiller`, `CapacityChangeEnrollmentHandler`, `EnrollmentCommandService`의 `CONFIRMED` 계산을 바꾸지 않았는가(설계명세 4.3)
- 남은 자리를 보여 주는 과정 상세 응답에 수료자가 반영되는가

## T4. 수료 처리

**변경 파일**
- 신규 `enrollment/CompletionRequest.java`: record `(@NotEmpty @Size(max = 200) List<@NotBlank @Size(max = 20) String> employeeIds)`. 검증 메시지는 한국어로 쓴다.
- 신규 `enrollment/CompletionFailureReason.java`: `NOT_CONFIRMED`, `ALREADY_COMPLETED`, `CANCELLED`, `NOT_ENROLLED`
- 신규 `enrollment/CompletionResponse.java`: `(List<String> completed, List<Failure> failed)`와 `Failure(String employeeId, CompletionFailureReason reason)`
- `enrollment/EnrollmentRepository.java`: `List<Enrollment> findBySessionIdAndEmployeeIdIn(Long sessionId, Collection<String> employeeIds)`
- 신규 `enrollment/CompletionService.java`
  - `@Transactional(isolation = READ_COMMITTED)`이다. 클래스를 따로 두는 것은 `EnrollmentCommandService` 비대화를 막기 위해서다.
  - `CompletionResponse complete(Long sessionId, List<String> employeeIds)`
    1. `findByIdForUpdate(sessionId)`를 첫 쿼리로 부르고, 없으면 `SessionNotFoundException`
    2. `session.ensureCompletable(clock.instant())`
    3. 요청 사번을 순서를 유지한 채 중복 제거(`LinkedHashSet`)
    4. 한 쿼리로 해당 사번들의 신청을 읽어 사번별로 묶는다
    5. 사번마다 판정한다. 순서는 활성 행(`CONFIRMED`면 `complete(now)`, `WAITING`이면 `NOT_CONFIRMED`), 그다음 `COMPLETED` 행(`ALREADY_COMPLETED`), 그다음 `CANCELLED` 행(`CANCELLED`), 그 밖에는 `NOT_ENROLLED`다.
    6. `saveAllAndFlush`
  - 응답 순서는 요청 순서를 따른다.

**테스트**
- 신규 `enrollment/CompletionServiceTest.java`(Mockito, C4~C7)
  - 시작 전 409 `SESSION_NOT_STARTED`, 미종료 409 `SESSION_NOT_CLOSED`, 이때 신청 조회를 하지 않는다
  - 없는 회차 404
  - `findByIdForUpdate`를 호출하고 `findById`는 호출하지 않는다
- 신규 `enrollment/CompletionIntegrationTest.java`(`@SpringBootTest`, 실제 MariaDB, C1~C3)
  - 회차를 만들고 확정·대기·취소·이미 수료·재신청 데이터를 둔다. 회차를 시작 후로 만들려면 고정 `Clock`이나 과거 `startAt`을 쓴다. 회차를 종료한 뒤 수료한다.
  - DB 상태를 확인한다(수료자는 `COMPLETED`·`completed_at`, 나머지는 불변, 대기자 그대로).
  - 정리는 `MyEnrollmentsQueryCountTest`처럼 자기 회차만 벌크 삭제한다. 고유 사번 접두어 `CP-`를 쓴다.

**완료 명령**
```bash
./gradlew spotlessApply test --tests "*CompletionServiceTest" --tests "*CompletionIntegrationTest"
```

**검토 포인트**
- 락이 첫 쿼리인가, 격리 수준
- 판정 우선순위(재신청 사원)
- 부분 성공이 한 트랜잭션에서 일관되게 반영되는가
- 대기자를 바꾸지 않는가(D-09, D-10)

## T5. 관리자 Controller와 OpenAPI

**변경 파일**
- 신규 `enrollment/EnrollmentAdminController.java`(`@RequestMapping("/api/v1/admin")`, `@Tag(name = "EnrollmentAdmin")`)
  - `GET /sessions/{sessionId}/roster` → `EnrollmentQueryService.getRoster`
  - `POST /sessions/{sessionId}/completions` → `CompletionService.complete`, 200
  - 두 메서드 모두 `@Parameter(hidden = true) @CurrentAdmin String adminId`를 받고, 메서드에 헤더 `@Parameter(in = HEADER, name = X-Employee-Id, required = true, schema maxLength 20)`를 붙인다.
  - 사번은 서비스로 넘기지 않는다. 권한 확인용이고, 감사 기록은 범위 밖이다.
  - `@Operation`과 `@ApiResponse`를 붙인다. 명단은 200, 400, 403, 404이고, 수료는 200, 400, 403, 404, 409(`SESSION_NOT_STARTED`, `SESSION_NOT_CLOSED`), 503이다.

**테스트**
- 신규 `enrollment/EnrollmentAdminControllerTest.java`(`@WebMvcTest`)
  - 관리자 목록은 `@TestPropertySource(properties = "eduhub.admin.employee-ids=TEST-ADMIN")`로 고정한다(OS 환경 변수 덮어쓰기 방지).
  - 명단 200(JSON 구조), 수료 200(completed·failed와 reason 문자열)
  - **권한 없음 403** `code=FORBIDDEN`, 서비스 미호출. 헤더 누락 400
  - 본문 400(빈 목록, 201개, 21자 사번, 공백 사번)
  - 404, **409 `SESSION_NOT_STARTED`**와 `SESSION_NOT_CLOSED`, 503
- `OpenApiDocsTest`
  - 두 경로의 summary와 tag `EnrollmentAdmin`
  - 헤더 `X-Employee-Id`가 required로 1회 나오고 `adminId` 파라미터가 없다
  - 응답 403·409가 있다

**완료 명령**
```bash

```

**검토 포인트**: 권한 검사가 서비스 호출 전에 일어나는가, 응답 계약이 설계명세 3절과 같은가
