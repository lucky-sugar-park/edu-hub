## T1. 스키마, 엔티티, Repository

**변경 파일**
- 신규 `src/main/resources/db/migration/V3__add_enrollment_waiting_key.sql`: 설계명세 4.1의 SQL 그대로. V1·V2는 수정하지 않는다.
- `enrollment/Enrollment.java`
  - 필드 `waitingKey`(`Long`, 컬럼 `waiting_key`)와 `confirmedAt`(`Instant`, 컬럼 `confirmed_at`), getter
  - public 생성자를 없애고 정적 팩터리로 바꾼다
    - `static Enrollment confirmed(CourseSession session, String employeeId, Instant now)`: 상태 `CONFIRMED`, `appliedAt = confirmedAt = now`, 키 null
    - `static Enrollment waiting(CourseSession session, String employeeId, Instant now, long waitingKey)`: 상태 `WAITING`, 키 부여, `confirmedAt` null
  - `void demote(long waitingKey)`: `CONFIRMED`가 아니면 `IllegalStateException`. 상태 `WAITING`, `confirmedAt = null`, 키 부여
- `enrollment/EnrollmentRepository.java`: 메서드 추가
  - `@Query("select max(e.waitingKey) from Enrollment e where e.session.id = :sessionId and e.status = 'WAITING'") Optional<Long> findMaxWaitingKey(Long sessionId)`, 같은 형태의 `findMinWaitingKey`
    - JPQL에 enum 리터럴 대신 `:status` 파라미터를 써도 된다
  - `long countBySessionIdAndStatusAndWaitingKeyLessThan(Long sessionId, EnrollmentStatus status, Long waitingKey)`
  - `List<Enrollment> findBySessionIdAndStatusOrderByConfirmedAtDescIdDesc(Long sessionId, EnrollmentStatus status, Pageable pageable)`
  - `Optional<Enrollment> findBySessionIdAndEmployeeIdAndStatusIn(Long sessionId, String employeeId, Collection<EnrollmentStatus> statuses)`
- 생성자 사용처를 팩터리로 바꾼다
  - `EnrollmentCommandService.enroll`: 확정이면 `confirmed(...)`
  - 대기이면 `waiting(..., findMaxWaitingKey(sessionId).orElse(0L) + 1)`
  - 이 키 부여까지가 T1 범위다. 순번 계산과 응답은 T2다.
  - 테스트 코드의 생성자 호출도 같은 방식으로 바꾼다.

**테스트** `enrollment/EnrollmentRepositoryTest.java`에 추가
1. `uk_enrollment_waiting_key`: 같은 회차·같은 키 두 건 → `DataIntegrityViolationException`, 다른 회차·같은 키는 허용, 키 NULL(확정) 여러 건 허용
2. `findMaxWaitingKey`/`findMinWaitingKey`: `WAITING`만 보고, 대기자가 없으면 `Optional.empty()`
3. `countBy...WaitingKeyLessThan`: 같은 회차의 더 작은 키만 센다
4. `findBy...OrderByConfirmedAtDescIdDesc` + `PageRequest.of(0, n)`: 늦게 확정된 순, 동률은 id 큰 순
5. `findBySessionIdAndEmployeeIdAndStatusIn`: 활성만 찾는다
- 엔티티 단위 테스트(신규 `enrollment/EnrollmentTest.java`): `confirmed`/`waiting` 팩터리 값, `demote` 성공, `WAITING`에서 `demote`하면 예외

**완료 명령**
```bash
./gradlew spotlessApply test --tests "*EnrollmentRepositoryTest" --tests "*EnrollmentTest" --tests "*EnrollmentCommandServiceTest" --tests "*CourseRepositoryTest"
```

**검토 포인트**
- V3 SQL이 설계와 같은지(보정 UPDATE, 유일 인덱스), V1·V2 무변경
- 팩터리의 필드 값
- 키 부여가 회차 락 안에서 일어나는지
- 기존 테스트가 의미를 잃지 않았는지

## 위험 영역

| 위험 | 대응 |
|---|---|
| V3의 보정 UPDATE(윈도 함수 + JOIN)가 MariaDB에서 실패하거나 개발 DB 데이터를 잘못 고침 | T1에서 `eduhub_test`에 적용해 확인. 개발 DB(`eduhub`)는 적용 전 대기 데이터를 개발자와 확인 |
| 강등 키가 기존 키와 충돌해 유일 제약 위반 | 키는 최솟값보다 작게만 부여(T4 D2), C6에서 확인 |
| `updateSession`에 락을 걸면서 관리자 수정이 신청과 직렬화되어 느려짐 | 3초 대기 힌트가 같은 락 쿼리에 있음. 초과 시 503 `LOCK_TIMEOUT` |
| `course → enrollment` 의존이 생김 | 인터페이스(`SessionCapacityChangeHandler`)로만 연결, T4 검토 포인트 |
| 강등과 신청이 동시에 일어날 때 순서 역전 | 둘 다 회차 락을 첫 쿼리로 잡음, C6 |
| 응답 필드 추가로 프런트 타입이 바뀜 | 필드 추가만(하위 호환), T6에서 클라이언트 재생성 후 프런트 테스트·빌드 |
