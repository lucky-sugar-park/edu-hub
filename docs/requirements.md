# EduHub 요구사항

## 개요
임직원이 사내 교육과정을 조회·신청하고, 정원이 차면 대기자로 등록되는 시스템.
- 사용자: 임직원(수강생), 교육 담당자(관리자)

## 기술 스택
- 백엔드: Java 21, Spring Boot 3, Spring Data JPA, Flyway, springdoc-openapi, MariaDB
- 프론트엔드: React 18 + TypeScript, Module Federation(shell, course-mfe, enrollment-mfe), MUI, Axios
- 빌드: Gradle(Kotlin DSL), npm workspaces

## 기능 요구사항 (무엇을 하는가)

| ID | 요구사항 | 사용자 | 우선순위 | 주차 |
|---|---|---|---|---|
| FR-01 | 교육과정 목록을 조회하고 제목·분류로 검색한다 (페이지 단위) | 임직원 | 필수 | 2 |
| FR-02 | 과정 상세와 회차(일정, 장소, 정원, 남은 자리)를 조회한다 | 임직원 | 필수 | 2 |
| FR-03 | 관리자는 과정과 회차를 등록·수정·종료한다 | 관리자 | 필수 | 2 |
| FR-04 | 회차에 수강 신청한다. 같은 회차에 중복 신청할 수 없다 | 임직원 | 필수 | 3 |
| FR-05 | 정원이 차면 대기자로 등록되고 대기 순번을 알려 준다 | 임직원 | 필수 | 3 |
| FR-06 | 신청을 취소하면 대기 1순위가 자동으로 신청 확정된다 | 임직원 | 필수 | 3 |
| FR-07 | 내 신청 내역(확정, 대기, 취소, 수료)을 조회한다 | 임직원 | 필수 | 4 |
| FR-08 | 관리자는 회차별 신청자·대기자 명단을 보고 수료 처리한다 | 관리자 | 보통 | 4 |
| FR-09 | 신청 확정·대기 승급 시 알림을 남긴다 (처음에는 로그·DB 기록) | 임직원 | 선택 | 5 |



## 비기능 요구사항 (얼마나 잘, 어떤 제약 아래서)
| ID | 분류 | 요구사항 | 확인 방법 |
|---|---|---|---|
| NFR-01 | \*\*정합성\*\* | 동시에 100명이 마지막 1자리에 신청해도 정원을 넘지 않는다 | 동시성 테스트 |
| NFR-02 | \*\*성능\*\* | 과정 목록 API는 데이터 1만 건에서 응답 300ms 이내, N+1 쿼리 없음 | 쿼리 로그, 성능 테스트 |
| NFR-03 | \*\*보안\*\* | 로그인한 사용자만 신청 가능, 본인 신청만 취소 가능, 비밀 정보는 저장소에 두지 않음 | 테스트, 비밀 검사 |
| NFR-04 | \*\*API 계약\*\* | 모든 API는 OpenAPI 문서가 있고, 프론트 클라이언트는 스펙에서 생성한다 | Swagger UI, 생성 스크립트 |
| NFR-05 | \*\*품질\*\* | 서비스 계층 테스트 커버리지 70% 이상, CI에서 빌드·테스트·포맷 검사 | CI 결과 |
| NFR-06 | \*\*운영성\*\* | 개발·테스트·운영 설정 분리, 사람이 직접 실행할 수 있는 빌드·배포·롤백 절차 문서 | 런북, 핫픽스 훈련 |
| NFR-07 | \*\*유지보수성\*\* | 도메인별 패키지(course, enrollment), 계층 규칙 준수, 화면은 MFE로 분리 | 리뷰, 아키텍처 테스트 |
| NFR-08 | \*\*이해도\*\* | 팀원 누구나 AI 없이 구조와 핵심 파일의 역할을 설명할 수 있다 | 발표 시 확인 |

## 결정 사항
| ID | 주제 | 결정 | 관련 요구사항 |
|---|---|---|---|
| D-01 | 대기자 취소 | 승급 없이 뒤 순번만 당겨진다 | FR-06 |
| D-02 | 정원 증가 | 늘어난 자리만큼 대기자가 순번대로 자동 승급한다 | FR-03, FR-06 |
| D-03 | 정원 감소 | 초과 인원은 가장 늦게 확정된 사람부터 대기로 바뀐다. 이들은 기존 대기자보다 앞 순번이며, 먼저 확정된 사람이 앞선다 | FR-03, FR-05 |
| D-04 | 회차 종료 | 회차 종료는 교육 완료를 뜻한다 | FR-03 |
| D-05 | 재신청 | 취소 후 같은 회차에 다시 신청할 수 있다. 자리가 있으면 바로 확정하고, 없으면 대기 맨 뒤로 간다 | FR-04, FR-05 |
| D-06 | 다른 회차 신청 | 같은 과정의 다른 회차에 동시에 신청할 수 있다 | FR-04 |
| D-07 | 취소·승급 기한 | 취소와 자동 승급은 교육 시작 전까지만 가능하다 | FR-06 |
| D-08 | 시작 후 변경 | 교육 시작 후에는 신규 신청과 정원 변경을 막는다 | FR-03, FR-04 |
| D-09 | 시작 후 대기자 | 교육 시작 후 남은 대기자는 대기 상태로 두고 승급 대상에서 제외한다 | FR-05, FR-07 |
| D-10 | 수료 처리 | 수료 처리는 회차 종료 후에만 가능하다. 수료하지 못한 확정자는 확정 상태로 두며, 별도의 미수료 상태는 두지 않는다 | FR-07, FR-08 |
| D-11 | 인증 방식 | Spring Security와 JWT 검증 구조로 시작하고, 개발 환경에서만 쓰는 로그인을 둔다. 사내 SSO는 나중에 연동한다 | NFR-03 |
| D-12 | 성능 측정 기준 | 로컬 MariaDB, 데이터 1만 건에서 p95 300ms 이내를 기준으로 한다 | NFR-02 |
| D-13 | CI·배포 환경 | CI는 GitHub Actions를 쓴다. 배포 대상은 확인이 필요하며, 정해질 때까지 Docker 이미지 빌드까지를 기준으로 한다 | NFR-05, NFR-06 |
| D-14 | DB와 실행 환경 | Docker를 쓰지 않고 Windows에서 실행하며, DB는 로컬 MariaDB를 쓴다 | NFR-01, NFR-02, NFR-06 |
| D-15 | 과정 종료 | 과정 종료는 모집 종료를 뜻한다. 종료된 과정은 수정하거나 회차를 추가할 수 없다. 등록된 회차는 그대로 두고 교육이 끝난 뒤 회차별로 종료한다. 종료된 과정의 회차에는 신규 신청을 받지 않는다 | FR-03, FR-04 |
| D-16 | 회차 종료 시점 | 회차는 교육 시작 후에만 종료할 수 있다(D-04). 열리지 않을 회차를 취소하는 기능은 나중에 정한다 | FR-03 |
| D-17 | 시작 후 회차 수정 | 교육 시작 후에는 정원과 시작 시각을 바꿀 수 없고 장소만 바꿀 수 있다. 시작 전에도 시작 시각을 현재보다 앞으로 바꿀 수 없다. 정원 변경에 따른 D-02, D-03 처리는 수강 신청(3주차)에서 구현한다 | FR-03 |
| D-18 | 관리자 API와 화면 경로 | 관리자 API는 `/api/v1/admin` 아래에 두고 인증(D-11)을 붙일 때 관리자 권한을 건다. 화면 경로는 react-router로 `/`(목록), `/admin`(관리), `/courses/:id`(상세)로 나눈다 | FR-02, FR-03, NFR-03 |
| D-19 | 중복 신청 방지 | MariaDB에는 부분 인덱스가 없으므로, 활성 신청(`CONFIRMED`, `WAITING`)일 때만 회차 id를 갖는 생성 컬럼 `active_session_id`와 사번에 유일 제약을 건다. 취소 등 비활성 신청은 제약에서 빠져 재신청(D-05)이 가능하다 | FR-04, D-05 |
| D-20 | 신청 동시성 | 신청 트랜잭션은 첫 쿼리로 회차 행에 비관적 쓰기 락을 잡고(과정 행은 잠그지 않음), 격리 수준은 `READ_COMMITTED`로 둔다. 락 대기는 3초이며 넘으면 503 `LOCK_TIMEOUT`을 돌려준다 | FR-04, NFR-01 |
| D-21 | 정원 초과와 신청자 식별 | 확정 수가 정원보다 적고 **대기자가 없을 때만** `CONFIRMED`로 저장한다. 그 밖에는 FR-04에서도 `WAITING`으로 저장해, 새 신청자가 기존 대기자를 앞지르지 않게 한다(정원 증가 후 승급 D-02가 들어오기 전에도). 대기 순번은 FR-05에서 부여한다. 인증(NFR-03) 전까지 신청자 사번은 요청 헤더 `X-Employee-Id`(문자열, 최대 20자)로 받는다 | FR-04, FR-05, NFR-03 |
| D-22 | 남은 자리 | 남은 자리는 `정원 - 확정 수`(0 미만이면 0)다. 회차 목록의 확정 수는 한 번의 집계 쿼리로 구한다. `course`가 `enrollment`에 의존하지 않도록 `course`에 확정 수 조회 인터페이스를 두고 `enrollment`가 구현한다 | FR-02, FR-04, NFR-02, NFR-07 |
| D-23 | 대기 순서 표현 | 대기자에게 정렬 키 `waiting_key`를 저장하고(작을수록 앞, 회차 안에서 유일), 대기 순번은 조회할 때 "키가 더 작은 대기자 수 + 1"로 계산한다. 새 대기자는 최댓값 + 1, 강등자는 최솟값보다 작은 키를 받는다. 대기에서 벗어나면 키를 지우므로 취소(D-01) 때 다른 행을 고치지 않는다. 내 순번은 `GET /api/v1/sessions/{sessionId}/enrollments/me`로 다시 볼 수 있고, 교육 시작 후에도 보여 준다 | FR-05, D-01, D-03, D-05, D-09 |
| D-24 | 정원 감소 강등과 정원 변경 락 | 관리자 회차 수정과 회차 종료도 회차 행 비관적 락을 첫 쿼리로 잡고 `READ_COMMITTED`로 실행한다(회차 행을 바꾸는 쓰기는 모두 같은 락, 3초 초과 시 503 `LOCK_TIMEOUT`). 정원이 확정 수보다 작아지면 `confirmed_at`이 가장 늦은 사람부터(동률은 id가 큰 쪽) 강등하고, 강등자끼리는 먼저 확정된 사람이 앞이 되도록 키를 준다. `course`는 `SessionCapacityChangeHandler` 인터페이스로 `enrollment`에 알린다. 정원 증가 승급(D-02)은 FR-06에서 같은 인터페이스에 추가한다 | FR-03, FR-05, D-02, D-03, D-20 |
| D-25 | 신청 취소 | 본인 신청 취소는 `POST /api/v1/sessions/{sessionId}/enrollments/me/cancel`로 하고, 행을 지우지 않고 `CANCELLED`와 `cancelled_at`을 남긴다. 확정·대기 모두 교육 시작 전까지만 취소할 수 있다(D-07, 시작 후 409 `SESSION_STARTED`). 과정이 종료(D-15)됐어도 시작 전이면 취소할 수 있다. 활성 신청이 없으면(이미 취소 포함) 404다. 응답에 승급자 정보는 넣지 않는다. 신청자 식별은 D-21의 임시 헤더를 따른다 | FR-06, D-05, D-07, D-15, NFR-03 |
| D-26 | 빈자리 채우기(승급) | 교육 시작 전 회차에서 확정 수가 정원보다 적으면 대기 키 오름차순으로 빈자리만큼 확정한다. 확정자 취소(FR-06)와 정원 증가(D-02)가 이 규칙을 같이 쓰고, 대기자 취소는 빈자리를 만들지 않아 승급이 없다(D-01). 승급자의 `confirmed_at`은 승급 시각이다. 취소·승급도 회차 행 락을 첫 쿼리로 잡고 `READ_COMMITTED`로 실행한다. 승급 알림은 FR-09에서 붙인다 | FR-06, D-01, D-02, D-07, D-09, D-20, NFR-01 |
